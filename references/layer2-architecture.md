# L2 · 架构上云（唯一真正挡住黑盒复刻和 REA 的一招）

这是全套里最有效的一层。REA 读不到服务端，黑盒复刻也猜不到服务端规则。目标：**让客户端里没有值钱的东西，复制品离开你服务端就是死壳。**

## 2.1 把价值搬到服务端

逐条问："这段逻辑泄露了，攻击者是不是就拿到了核心价值？" 是 → 搬服务端。

必须在服务端的：
- **核心算法 / 模型 / 定价 / 推荐 / 匹配逻辑**
- **权限与会员判断**（永远不信客户端说"我是会员"）
- **风控规则**
- **任何密钥、加密密钥、第三方 API Key**

客户端只保留：展示、交互、把请求转发给服务端。

## 2.2 服务端绑定执行（让复制品跑不起来）

对抗"抄走完整客户端"的终极手段：**关键步骤离开服务端就无法完成。**

做法（按强度递增）：
1. **关键数据按需下发**：客户端启动/操作时才从服务端取必要数据，不本地缓存全量。
2. **关键运算走服务端**：核心计算发请求、服务端算、返回结果。客户端没有算法本体。
3. **会话级密钥**：核心功能用的密钥由服务端在鉴权后下发，用完即弃，不落地。
4. **分步校验**：一个完整业务拆成多步，每步都要服务端签发的 token 才能进下一步。重放/离线即断。

效果：攻击者 1:1 复制了客户端 → 一断开你的服务端，它什么也做不了，因为"怎么做"从没发给过他。

## 2.3 接口设计防黑盒推测

黑盒复刻靠大量调你的接口来猜规则。对抗：
- 接口只返回"结果"，不返回"中间量/置信度/规则参数"（别帮它反推）。
- 同样输入加入服务端侧随机/个性化，让它采样到的"输入→输出"对噪声大、难拟合。
- 配合 L4 的限流，让大规模采样成本高到不值。

## 2.5 协议与流量保护（打 REA 的 pcap/TShark 线）

REA 能解析抓包（TShark）来还原你的客户端-服务端协议。对抗：
- **全链路 TLS**，别用明文协议传业务数据。
- **证书绑定（pinning）**，防中间人抓明文（配合 L3 检测 pinning 被绕）。
- **请求/响应体再加一层应用层加密 + 签名**，就算 TLS 被用户侧代理解了，抓到的也是密文。
- **协议里不暴露逻辑**：字段名别自带语义（别叫 `is_vip`/`final_price_before_discount`），别回传中间计算量。
- 防重放：时间戳 + nonce + 服务端签名。

## 2.6 智能合约 / 链上代码（打 REA 的 EVM 线）

链上字节码是公开的，REA 用 EVM 反编译能读。对抗思路不同：
- **链上只放必须公开可验证的最小逻辑**，专有算法/参数放链下服务端或用预言机喂入。
- 关键参数可升级（代理合约），别把"值钱的常量"硬编码在链上。
- 这类场景"防读"基本不可能，重心放在"读了也复制不了你的链下供给/数据"。

## 2.4 密钥卫生（硬红线）
- 客户端**绝不**打包 API Key、加密私钥、数据库凭据。
- 第三方服务调用走服务端代理，客户端只认自己后端。
- selfcheck 会扫客户端产物里的疑似密钥（高熵串、`api_key=`、私钥头）。

## 验收
- [ ] recon 列出的"客户端暴露核心资产"已清零（全部服务端化）
- [ ] 客户端离线 / 断开你的服务端后，核心功能无法运行（已实测）
- [ ] 客户端产物内无任何明文密钥 / 私钥
- [ ] 接口不返回可用于反推规则的中间量
